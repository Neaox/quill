Added: Sign in with the organisation's identity provider. The sign-in page now offers "Continue with Microsoft", "Continue with Google" and the like above the password form whenever an instance has configured one, and a provider is a data preset rather than a code path: Microsoft Entra ID (with the tenant pinned), Google Workspace (with the hosted domain checked), Amazon Cognito, Auth0, and a generic OpenID Connect provider for anything discovery can describe. Configuration is `OIDC_PROVIDERS` plus per-provider variables, validated at boot so a misconfigured provider is a server that refuses to start rather than a button that fails when somebody presses it.
Security: The OpenID Connect flow is Authorization Code with PKCE (`S256`) and nothing else: `state` and `nonce` are minted per attempt and bound to a ten-minute `__Host-` cookie, discovery and the provider's key set are fetched through the SSRF-safe outbound client and cached, and the id token is verified against the published keys — with the algorithm chosen from an allowlist rather than from the token, a `crit` header refused outright, and keys below the RSA and curve floors ignored — before a single claim in it is believed. A federated account is keyed by issuer and subject rather than by email, so changing an address at the provider moves no account. Attaching an identity to an account that already exists requires a verified address on both sides: the provider must vouch for it and the account must already have proved it, so nobody can sign up with somebody else's work address, leave the mail unopened, and be handed the account when its real owner first signs in. Linking can be turned off per provider, creating an account can be turned off per provider, and a link revokes every other session that account holds. Every outcome is audited without any part of a token, and every failure answers the browser identically, so nobody can use a sign-in button to discover which addresses have accounts.
