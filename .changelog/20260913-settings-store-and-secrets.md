Added: An organisation's settings — its name and logo, its theme, the default layout, the public site's navigation, and the share-link and publishing policies — are now stored as a versioned YAML file in a system workspace of the content store, written through the same publish path documents are, so every change has an author, a change note, and a history, and a whole configuration moves to another instance by being copied.
Added: A workspace can carry its own layout override, which its organisation may lock; `GET /api/workspaces/:id/settings` answers with the layout it actually renders with and says whether the workspace or the organisation decided it.
Added: Two administrators changing the same settings file at once no longer overwrite each other: a write states the revision it was based on, and one whose file has changed underneath is refused with a conflict rather than merged. Changing a different settings file in between is not a conflict.
Added: Secrets entered in the product — OIDC client secrets, SMTP passwords, integration tokens — are stored under envelope encryption: each gets its own AES-256-GCM data key, wrapped by an instance master key that never reaches the database. Settings files reference a secret by name and never by value, so a copied settings file is complete and harmless.
Added: `GET/PUT/DELETE /api/settings/secrets/:name` and `GET /api/settings/secrets` let an instance administrator manage secrets without any of them ever answering with a value; the audit trail records the name and the key that wraps it and nothing else.
Added: The master key comes from `QUILL_MASTER_KEY` or from a key file on a mounted volume, and `pnpm --filter @quill/server secrets:rotate` re-wraps every data key without touching a single ciphertext. An instance that serves anything but localhost refuses to boot without a key rather than inventing one the next deployment would not have, and refuses the published all-zero development key by value.
Security: A secret's ciphertext is bound to the name it is stored under, and its wrapped data key to the master key that wrapped it, as authenticated data. Somebody who can write the secrets table but cannot read the master key can no longer move one secret's row into another's name and have the application use it as that secret.
Security: A master key file that anybody but its owner can read is refused rather than warned about, and a master key that is not exactly thirty-two bytes of standard base64 is refused rather than silently decoded into a different key that would leave every stored secret unopenable.
Security: An instance whose public address is not localhost now requires an explicit master key whatever `NODE_ENV` says — the same signal the session cookie takes its `Secure` flag from — so a deployment cannot be strict about its cookies and lax about the key that wraps every secret in it.
Security: A public-site navigation link must be a rooted path or an `http(s)` address, so a `javascript:` or `data:` link cannot be saved into the header every anonymous reader sees.
Security: A master-key rotation re-wraps each secret only while the row still carries the envelope it read, so a rotation running beside an administrator replacing that secret can no longer leave the new value unopenable.
