# Security review: M1 authentication, sessions, authorisation, and rendering

**Date:** 2026-09-12
**Reviewer:** automated security review (read-only)
**Standard:** `docs/architecture/decisions/0011-authentication-and-security-baseline.md` (ADR-011), `docs/security/checklist.md`. Context: ADR-021 (locking API contract), ADR-031 (render caching).
**Scope:** `apps/server/src/auth/**`, `apps/server/src/plugins/{session,error-handler,request-id}.ts`, `apps/server/src/application/{auth-service,permissions}.ts`, `apps/server/src/routes/{auth,me,units,workspaces,documents,drafts,locks}.ts`, `apps/server/src/infrastructure/repositories/{session,credential,magic-link,user}-repository.ts`, `apps/server/src/infrastructure/db/schema.ts`, `apps/server/src/config.ts`, `apps/server/src/main.ts`, `packages/markdown/src/render/**`, `packages/markdown/src/directives/**`, `apps/web/src/lib/**` and `apps/web/src/features/auth/**` (not yet built).

**Note on concurrency:** `apps/server` and ADR-011 itself changed during this review (other agents are active per the task brief). ADR-011 gained an "Enterprise single sign-on" section (OIDC/SAML presets, M3 scope) while this review was in progress; it does not change any M1-scope requirement this report checks against. No other change to the sections relied on here was observed. Everything below reflects the files as read at review time; re-verify anything already mid-edit before acting on it.

## Executive summary

1. **Critical:** documents, drafts, and locks have almost no authorisation — any signed-in user, from any workspace or unit, can read/overwrite any document's draft and acquire/heartbeat/release any document's lock (`routes/documents.ts`, `routes/drafts.ts`, `routes/locks.ts`), confirmed by the tests themselves.
2. **Critical:** session ids are stored in plaintext in Postgres and are `crypto.randomUUID()` (~122 bits), not the hashed 256-bit token ADR-011 mandates — a DB read yields directly usable session cookies (`schema.ts`, `session-repository.ts`, `uuid-generator.ts`).
3. **Critical:** the Markdown renderer never sanitises anything — `allowDangerousHtml: true` end to end, no `rehype-sanitize` in the codebase or dependency tree, raw `<script>`/event handlers and `javascript:` URLs pass straight through (`packages/markdown/src/render/html.ts`).
4. **High:** sign-up leaks account existence via a `409 email_taken` status, tested and asserted as intended behaviour — a direct violation of the no-enumeration rule.
5. **High:** sign-in has a timing side channel (no dummy hash verify for a missing user/credential), rate limiting is entirely unwired (dependency not even installed), and there is no breached-password (HIBP) check anywhere.
6. **High:** password length policy is 8–unbounded instead of ADR-mandated 12–128, and there is no CSRF defence (`Sec-Fetch-Site`/`Origin`) or any security-header plugin (CSP, HSTS, X-Content-Type-Options, etc.) at all.
7. **Medium:** the session cookie's `Secure` flag is derived from `NODE_ENV` rather than the scheme of `appUrl`, and the cookie lacks the `__Host-` prefix — a misconfigured deployment can silently ship sessions over plaintext HTTP.
8. **Medium:** `GET /api/workspaces/:id` and workspace document listings require only *a* session, not membership, leaking cross-tenant workspace/document metadata; magic-link/reset tokens are not superseded when a newer one is requested.
9. **Medium:** Argon2id parameters are never passed explicitly (current library defaults happen to meet the OWASP floor, but this is unverified by test and there is no re-hash-on-raise path); email verification is tracked but never enforced on any route beyond `/api/me`.
10. **Not built yet:** OIDC/passkeys/share links/outbound-request SSRF protection/uploads/`apps/web` auth UI are all M2+ and out of scope for a pass/fail today; each is called out below with what must be true when it lands.

## Findings by severity

### Critical

**1. Cross-tenant broken access control on document reads, drafts, and locks**
- **Location:** `apps/server/src/routes/documents.ts` (`GET /api/documents/:id`, `GET /api/workspaces/:workspaceId/documents`), `apps/server/src/routes/drafts.ts` (`GET`/`PUT /api/documents/:id/draft`), `apps/server/src/routes/locks.ts` (`acquire`/`heartbeat`/`release`; only `takeover` checks `isWorkspaceAdmin`).
- **What an attacker could do:** Any user who can create a session anywhere in the instance (including a freshly self-registered, unverified account — see Finding 9) can read any other tenant's document metadata and full draft AST, overwrite any document's draft content (`PUT .../draft` only checks `sessionId` against the lock row, not workspace membership), and acquire/steal/release any document's edit lock — causing data loss or denial of editing across tenants. `routes/documents.integration.test.ts` demonstrates this directly: a `MEMBER` user with **zero grants** on the workspace under test successfully calls `POST /api/documents/:id/lock/acquire` and receives `409 held` (a legitimate contention response, not `403 forbidden`), proving the route never checked whether `MEMBER` belongs to that workspace at all.
- **Fix:** Add a workspace/document-membership check (at minimum "does this user have any grant on this document's workspace," pending the full ADR-012 tenancy resolver) as a `preHandler` or inline guard on: `GET /api/documents/:id`, `GET`/`PUT /api/documents/:id/draft`, `POST /api/documents/:id/lock/{acquire,heartbeat}`, `DELETE /api/documents/:id/lock`, `GET /api/workspaces/:id`, and `GET /api/workspaces/:workspaceId/documents`. Resolve the document's `workspaceId` first (as `documents.ts`'s `PATCH`/`DELETE` already correctly do), then call `permissions.isWorkspaceAdmin` or a new, less strict `isWorkspaceMember` before touching the resource.
- **Test that should prove the fix:** An integration test creating two workspaces (A, B) and a document in B; a user with a grant only in A calls `GET /api/documents/:id` (B's document), `GET`/`PUT .../draft`, and `POST .../lock/acquire` on B's document and asserts `403`/`404` on each, where today they succeed (or fail only for unrelated reasons like lock contention).

**2. Session ids are unhashed, non-ADR-strength, and directly usable from a database read**
- **Location:** `apps/server/src/infrastructure/db/schema.ts` (`sessions.id`, `documentLocks.holderSessionId`), `apps/server/src/infrastructure/repositories/session-repository.ts`, `apps/server/src/infrastructure/uuid-generator.ts`, `apps/server/src/application/auth-service.ts` (`issueSession`).
- **What an attacker could do:** ADR-011 requires the session cookie to carry a 256-bit random id whose *hash* is what's stored, "so a database read never yields a usable token" (mirroring the magic-link design, which does this correctly). Here, `issueSession` sets `sessions.id` to `ids.uuid()` — a `crypto.randomUUID()`, i.e. the literal value later placed in the cookie — with no hashing step at all. Anyone with read access to the `sessions` table (a backup, a read replica, a misconfigured admin panel, a future SQL-injection bug elsewhere, an over-broad support query) obtains ready-to-use session cookies for every currently-authenticated user, i.e. instant account takeover instance-wide, with no way to detect or invalidate it short of rotating every session. Separately, `crypto.randomUUID()` also has less entropy (~122 bits from the version/variant-constrained UUIDv4) than the 256 bits ADR-011 specifies, though this is the smaller of the two problems.
- **Fix:** Reuse the existing, correct pattern from `auth/tokens.ts`: generate the session token with `generateToken()` (`randomBytes(32)` → base64url), store only `hashToken(token)` in the `sessions` table (rename `sessions.id` to a hash column, or add a separate opaque primary key plus a unique `token_hash` column), set the *raw* token in the cookie, and change `findById`/heartbeat lookups in `session-repository.ts` and `lock`/`draft` repositories (which currently store/compare the raw session id via `holder_session_id`) to hash the incoming cookie value before querying.
- **Test that should prove the fix:** After `POST /api/auth/sign-in`, assert the value the server returns in the `Set-Cookie` header is **not** equal to any column value in the `sessions` row created for that request (query the test database directly), and that `/api/me` still succeeds using the cookie.

**3. The Markdown renderer emits raw script, event handlers, and `javascript:`/`data:` URLs unsanitised**
- **Location:** `packages/markdown/src/render/html.ts` (`renderHtml`: `allowDangerousHtml: true` passed to both `remarkRehype` and `rehypeStringify`), `packages/markdown/src/render/handlers.ts` (`image` handler passes `node.url` straight to `src`; no handler overrides plain `link` nodes, so default remark-rehype passes `href` through unfiltered).
- **What an attacker could do:** ADR-011 is explicit: "Rendered Markdown is sanitised: raw HTML in documents is passed through an allowlist sanitiser (rehype-sanitize...) ... strips scripts, event handlers, `javascript:` and `data:` URLs except images," and lists this as a hard *Consequence* ("The Markdown renderer gains the sanitiser before any rendered content is served"). Today, nothing in the repository does this — `rehype-sanitize`, `sanitize-html`, and `DOMPurify` do not appear in any `package.json` or source file. Any document author (or any content pipeline that feeds markdown into `renderHtml` — imports, templates, comments once they exist) can write `<script>...</script>`, `<img onerror="...">`, `[click me](javascript:...)`, or `![x](javascript:...)` in Markdown source and have it emitted byte-for-byte into the HTML string this function returns. This is a stored-XSS-shaped hole waiting for its first consumer: since the ADR frames sanitisation as the renderer's own job ("the Markdown renderer gains the sanitiser"), not a downstream caller's, the very first place `renderHtml`'s output reaches a browser (the M2 reading view / render cache per ADR-031) will be exploitable unless this is fixed first.
- **Fix:** Add `rehype-sanitize` inside `renderHtml` itself (between the `remarkRehype` and `rehypeStringify` stages), with an explicit schema allow-listing exactly the elements/attributes the renderer's own handlers emit (headings with `id`, `a.heading-anchor` with `href`/`aria-label`, `pre`/`code` with `data-lang`/`data-tokens`, `img` with `src`/`alt`/`title`, table elements, the `aside`/`section`/`div` wrappers with their fixed `className`s, etc.) plus a conservative safe-HTML subset for raw author HTML, explicitly stripping `<script>`/`<style>`/event-handler attributes (`on*`) and rejecting `javascript:`/`data:` URL schemes in `href`/`src` (except `data:image/*` for images, per the ADR). Do not leave this to "the caller."
- **Test that should prove the fix:** `renderHtml` unit tests feeding `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `[x](javascript:alert(1))`, and `![x](javascript:alert(1))` through a document AST, asserting the returned HTML string contains none of `<script`, `onerror=`, or `javascript:`.

### High

**4. Sign-up leaks account existence by status code (account enumeration)**
- **Location:** `apps/server/src/routes/auth.ts` (`POST /api/auth/sign-up` → `throw new AppError(409, 'email_taken', ...)`), confirmed intentional by `apps/server/src/routes/auth.integration.test.ts` ("rejects sign-up with a duplicate email" asserts `409`/`email_taken`).
- **What an attacker could do:** Submit any email to sign-up and learn instantly, with a distinct status code and error body, whether that email already has an account — directly contradicting ADR-011's "No account enumeration: sign-up... always answer[s] in constant shape... whether or not the email exists," which the same document lists as a hard requirement alongside sign-in/magic-link/reset (which *do* behave correctly today).
- **Fix:** Make sign-up behave like `requestMagicLink`/`requestPasswordReset`: always return the same success shape (e.g. `202`, "check your email to finish creating your account"), and handle the collision case out-of-band — e.g. send the existing owner a "someone tried to sign up with your email; sign in instead" notice rather than telling the caller synchronously.
- **Test:** A test asserting sign-up with a pre-existing email and sign-up with a fresh email return identical status codes and body shapes (differing only in fields that must differ, e.g. no `userId`), and that no immediate synchronous signal distinguishes them.

**5. Sign-in has a timing side channel that distinguishes "no such account" from "wrong password"**
- **Location:** `apps/server/src/application/auth-service.ts` (`signIn`): returns immediately when `user === null` or `credential === null`, and only calls `verifyPassword` (an intentionally slow Argon2id operation) when a credential exists.
- **What an attacker could do:** Measure response latency to distinguish "email not registered" / "no password set for this account" (fast path, no hashing) from "email registered, wrong password" (slow path, one Argon2id verify) — an enumeration channel that survives even though the response body/status are already identical, undermining ADR-011's "constant shape **and similar time**."
- **Fix:** Always perform one `verifyPassword` call against a fixed dummy hash when no real user/credential is found, so both branches pay the same cost.
- **Test:** Spy on `verifyPassword` (or the underlying `verify` from `@node-rs/argon2`) and assert it is invoked exactly once for every `signIn` call regardless of whether the account exists.

**6. No rate limiting anywhere on authentication endpoints**
- **Location:** `apps/server/src/auth/rate-limit.ts` (`createNoopRateLimiter`, documented as an unwired seam), `apps/server/src/routes/auth.ts` (never calls it), `apps/server/package.json` (no `@fastify/rate-limit` or equivalent dependency at all).
- **What an attacker could do:** Brute-force passwords against `/api/auth/sign-in` at unlimited speed, mail-bomb any address via `/api/auth/magic-link` or `/api/auth/password-reset/request` (both accept an arbitrary email with no cap), and burn SMTP sending quota / harass a victim's inbox, all without friction.
- **Fix:** Wire a real limiter (in-process token bucket is enough for a single instance; a shared store is needed once there's more than one process, as the seam's own comment anticipates) into `sign-in`, `sign-up`, `magic-link`, and `password-reset/request`, keyed by account and by source IP, with exponential backoff rather than hard lockout (per ADR-011, to avoid attacker-triggered victim lockout).
- **Test:** Hammer `/api/auth/sign-in` with a wrong password past the configured threshold and assert a `429` response; assert the correct password still works once the backoff window elapses (via the fake clock already used elsewhere in this codebase's tests).

**7. No breached-password (HIBP) check**
- **Location:** Absent everywhere; confirmed by `grep -ri "hibp\|breach\|pwned"` across the repository returning nothing, and by `application/auth-service.ts`'s `signUp`/`resetPassword` calling `hashPassword` directly with no prior check.
- **What an attacker could do:** Users (including admins) can set commonly-breached passwords (`password123`, etc.), which credential-stuffing tooling will try first — the exact risk ADR-011's HIBP requirement exists to reduce.
- **Fix:** Implement the HIBP k-anonymity range API (SHA-1 prefix lookup) with the ADR-specified local fallback list for when the service is unreachable; call it from `signUp` and `resetPassword` before hashing, rejecting with a clear, non-enumerating error message.
- **Test:** Mock the HIBP client to report a submitted password as breached and assert sign-up/reset are rejected; mock it as unreachable and assert the local fallback list is consulted instead of silently allowing anything through.

**8. Password length policy is 8–unbounded instead of the ADR's 12–128; no CSRF checks; no security headers**
- **Location:** `apps/server/src/routes/auth.ts` (`SignUpBody`, `ResetPasswordBody`: `Type.String({ minLength: 8 })`, no `maxLength`); whole-repo absence of `Sec-Fetch-Site`/`Origin` checks and of any CSP/HSTS/`X-Content-Type-Options`/`Referrer-Policy`/`Permissions-Policy`/`Cross-Origin-Opener-Policy` header logic (`app.ts`, `plugins/*`, `package.json` — no `@fastify/helmet` or manual equivalent).
- **What an attacker could do:** (a) Weaker-than-specified minimum length increases brute-force/credential-stuffing success; an unbounded maximum lets a caller submit a multi-megabyte "password" and force the server to run expensive Argon2id hashing over it repeatedly — a cheap CPU-exhaustion DoS vector. (b) With no `Sec-Fetch-Site`/`Origin` check and a cookie that is neither `__Host-` scoped nor guaranteed `Secure` (Finding 11), the app's only CSRF defence is the browser's default `SameSite=Lax` handling, which the ADR itself says should be reinforced with an explicit check precisely because it's the sole defence (no CSRF tokens exist as a backstop). (c) With no CSP, any HTML injection anywhere in the app's surface (including the unsanitised renderer in Finding 3) becomes trivially exploitable, since there is no `default-src`/`script-src` restriction to blunt it, and there's no `X-Content-Type-Options: nosniff`/`Cross-Origin-Opener-Policy` hardening against MIME-sniffing or cross-origin window reference attacks either.
- **Fix:** Change both schemas to `Type.String({ minLength: 12, maxLength: 128 })`. Add a `preHandler`/`onRequest` hook applied to all state-changing routes rejecting requests whose `Sec-Fetch-Site` header (when present) isn't `same-origin`/`none`, or whose `Origin` header (when present) doesn't match `config.appUrl`. Add `@fastify/helmet` (or an equivalent manual `onSend` hook) configured per ADR-011's exact header list, including a per-response CSP nonce plumbed into any server-rendered HTML once that exists.
- **Test:** Sign-up with a 8–11 char password → `400`; with a 129+ char password → `400`; with 12–128 → accepted. A state-changing POST with `Origin: https://evil.example` → `403`; with a matching `Origin` → success. An integration test asserting the documented headers are present with the documented values on a representative response.

### Medium

**9. Session cookie `Secure` flag depends on `NODE_ENV`, not the app URL's scheme; cookie lacks `__Host-`**
- **Location:** `apps/server/src/config.ts` (`secureCookie: env.SECURE_COOKIES === undefined ? env.NODE_ENV === 'production' : ...`, `cookieName: env.SESSION_COOKIE_NAME ?? \`${BRAND.slug}_session\``).
- **What an attacker could do:** ADR-011 permits a non-`Secure` cookie only when `appUrl` is literally `http://localhost`. Here, the deciding factor is `NODE_ENV`, a variable many deployment platforms don't set to `production` by default (containers, some PaaS setups, a staging box someone forgot to configure) even when `APP_URL` is a real HTTPS domain. In that misconfiguration, session cookies are issued without `Secure` over what should be an HTTPS-only deployment, and a network attacker able to force or observe a plaintext HTTP request (downgrade, a stray `http://` link, a shared network) can capture the session id in transit. Separately, without the `__Host-` prefix, the browser does not enforce that the cookie was actually set with `Secure`/`Path=/`/no `Domain` — the guarantee ADR-011 relies on the prefix for is simply absent.
- **Fix:** Derive `secureCookie` from the scheme of `appUrl` (`new URL(appUrl).protocol === 'https:'`), defaulting to `false` only when the host is `localhost`/`127.0.0.1`, rather than trusting `NODE_ENV`. Rename the cookie to `__Host-${BRAND.slug}_session` (Path=/ and no Domain are already satisfied by `session-cookie.ts`).
- **Test:** `loadConfig({ APP_URL: 'https://app.example.com' })` with no `NODE_ENV`/`SECURE_COOKIES` set asserts `secureCookie === true`; `loadConfig({ APP_URL: 'http://localhost:3000' })` asserts `secureCookie === false`; the configured cookie name starts with `__Host-`.

**10. Cross-tenant workspace/document-list disclosure**
- **Location:** `apps/server/src/routes/workspaces.ts` (`GET /api/workspaces/:id`), `apps/server/src/routes/documents.ts` (`GET /api/workspaces/:workspaceId/documents`) — both gated only by `app.requireSession`, explicitly noted in a code comment as "reading an existing workspace only requires a session."
- **What an attacker could do:** Any signed-in user anywhere in the instance can read any other tenant's workspace name/slug/unit id, and list every document (id, slug, path, title, status) in a workspace they have no grant on, simply by knowing or guessing its id — a direct instance of the pattern ADR-011 rules out ("there is no route that trusts a workspace id from the path without checking membership").
- **Fix:** Require at least workspace membership (any role, not just admin) before returning a workspace or its document list, using the same permissions/tenancy seam already used for admin gating.
- **Test:** A user with no grant on workspace B receives `403`/`404` from `GET /api/workspaces/B` and `GET /api/workspaces/B/documents`.

**11. Magic-link/reset tokens are not invalidated when a newer one is requested**
- **Location:** `apps/server/src/application/auth-service.ts` (`issueMagicLink`).
- **What an attacker could do:** ADR-011 requires a token to be "invalidated by any newer token for the same purpose." Today, requesting a second password-reset (or sign-in, or verification) link leaves the first one fully valid until its own 15-minute expiry. A stale reset email sitting in an inbox, or a link a user clicked and closed without completing, remains a live credential-reset vector for up to 15 minutes after the user believed they'd moved on to a newer link.
- **Fix:** In `issueMagicLink`, before inserting the new token, mark any existing unconsumed rows for `(userId, purpose)` as consumed (or add an expiring `WHERE` clause equivalent) so only the newest token for a given purpose is ever valid.
- **Test:** Request two password-reset links for the same account; attempt to consume the first — assert it now fails with `invalid_or_expired` even though its own 15-minute window hasn't elapsed.

**12. Email verification is tracked but never enforced**
- **Location:** `emailVerifiedAt` (`schema.ts`, `user-repository.ts`) is set correctly and exposed via `GET /api/me` (`routes/me.ts`), but no route in scope — `workspaces.ts`, `units.ts`, `documents.ts`, `drafts.ts`, `locks.ts` — checks it.
- **What an attacker could do:** ADR-011: "Email verification is required before a user can be granted anything beyond their own profile." A self-registered account that never verifies its email (or one whose verification link a mail scanner consumed, invalidating it for the real user) has identical capabilities to a verified one for every grant it holds, undermining the assumption that only verified addresses can act.
- **Fix:** Add an `emailVerified` gate — either inside `requireSession`/a new `requireVerifiedSession` preHandler, or as a check inside `permissions.ts` — applied to every route beyond `/api/me` and the auth routes themselves.
- **Test:** Sign up, skip verification, and confirm a mutation the account would otherwise be entitled to (e.g. creating a document in a workspace it's an admin of) is rejected until `POST /api/auth/verify-email` succeeds.

### Low

**13. Argon2id parameters are relied on implicitly rather than pinned**
- **Location:** `apps/server/src/auth/password.ts`.
- **What an attacker could do:** Nothing today — `@node-rs/argon2@2.2.1`'s defaults (`m=19456, t=2, p=1`) meet the OWASP floor ADR-011 cites. The risk is a silent regression: a future dependency bump that changes the library's defaults would weaken every new hash with no test or code path to notice, and there is no re-hash-on-sign-in mechanism to migrate existing hashes if parameters are deliberately raised later.
- **Fix:** Pass `memoryCost`/`timeCost`/`parallelism` explicitly in `hashPassword`; add a parameter-check in `signIn` that re-hashes and persists (via `credentials.upsert`) whenever a verified hash's encoded parameters fall below the currently configured target.
- **Test:** Decode the PHC string `hashPassword` returns and assert its `m=`/`t=`/`p=` fields match the configured constants; simulate a sign-in against a hash encoded with lower parameters and assert `credentials.upsert` is called with a freshly re-hashed value.

**14. Swagger UI and OpenAPI JSON are served by default with no environment gate**
- **Location:** `apps/server/src/plugins/openapi.ts` (`serveUi` defaults from `app.ts`'s `serveApiDocs ?? true`), `apps/server/src/main.ts` (calls `buildApp` without passing `serveApiDocs`, so production gets the default `true`).
- **What an attacker could do:** Browse the full route/schema surface at `/api/docs` and `/api/openapi.json` in any deployment that doesn't explicitly opt out — low severity while the API is a skeleton, but worth closing before real routes and internal-only endpoints accumulate.
- **Fix:** Default `serveApiDocs` from an explicit config flag (e.g. `config.appEnv !== 'production'`) rather than hard-coding `true`, and have `main.ts` pass it through.
- **Test:** `buildApp({ deps })` built against a config with a production-like environment does not register `/api/docs`.

**15. Dev mailer logs the raw magic-link token to stdout by default**
- **Location:** `apps/server/src/auth/dev-mailer.ts`, selected whenever `MAIL_DRIVER` is unset (`config.ts` defaults `MAIL_DRIVER` to `'dev'`).
- **What an attacker could do:** Nothing in an actual local-dev context (this is the intended behaviour, and the comment says as much). Flagging only because the *default* driver, absent explicit configuration, logs live sign-in/reset/verification tokens to process stdout — worth a deployment-time check that any shared/staging environment explicitly sets `MAIL_DRIVER=smtp`, since nothing in the code itself prevents `dev` from being selected outside a developer's own machine.
- **Fix/verification:** Not a code fix — confirm via deployment configuration/CI that `MAIL_DRIVER=smtp` (or another real mailer) is always set outside local development; consider `config.ts` refusing to boot with `MAIL_DRIVER=dev` when `NODE_ENV=production` (mirroring the "secrets never have defaults" posture the file already documents for everything else) once the app-environment signal from Finding 9 exists.

## Not applicable yet (feature not built) — what must hold when it lands

- **OIDC (ADR-011 "Identity and credentials," and the newly added "Enterprise single sign-on" section):** PKCE, `state`/`nonce`, issuer/audience validation against JWKS, tenant/hosted-domain pinning per preset, `email_verified` required before trusting a federated email, tokens never stored client-side.
- **Passkeys:** discoverable credentials, required user verification, sign-count regression detection.
- **Share links:** the `shareLinks` table (schema.ts) already has the right shape (`tokenHash`, `expiresAt`, `passwordHash`, `revokedAt`); the route/service layer that creates/consumes them must reuse `auth/tokens.ts`'s hash-at-rest pattern and write an audit row per use.
- **Outbound HTTP client (embeds, source references):** host allowlist per integration, DNS resolution checked against private/link-local ranges (SSRF), redirect limits with re-checking, timeouts, response size caps — must exist before the first such integration, per ADR-011's own Consequence.
- **Uploads:** size limits, sniffed (not client-supplied) content type, image re-encoding, SVG sanitisation, a non-executing serving origin/path prefix.
- **`apps/web/src/lib/**` and `apps/web/src/features/auth/**`:** neither directory exists yet (`apps/web/src` currently has only `app/`, `features/design`, `features/home`, `features/theme`, `main.tsx`, `styles/`). When the sign-in/sign-up/magic-link UI is built: never put a token in a URL the browser will keep in history/referrer beyond the initial magic-link/reset navigation itself; validate the post-sign-in redirect target against an allowlist of same-origin paths (no open redirect via a `?next=`-style parameter); never let client JS read the session cookie (already `HttpOnly` server-side, so this should hold by construction — verify no parallel non-HttpOnly token is introduced for the SPA's convenience).
- **`render_cache` table / publish-time render consumer (ADR-031):** correctly not yet built (no such table in `schema.ts`). When it lands, the sanitiser from Finding 3 must run **before** anything is written to that cache, per ADR-031's own framing of the renderer's contract.
- **Rate limiting:** the seam (`auth/rate-limit.ts`) exists but is unimplemented; see Finding 6, which treats this as a live gap rather than N/A since the ADR requires it for the M1 surface that already exists (sign-in, sign-up, magic-link, reset).
