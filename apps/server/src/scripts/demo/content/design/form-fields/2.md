# Form fields

Forms are where Tidepool customers do their real work: importing feedback, inviting teammates, configuring a roadmap. A form that is slightly hard to use costs us support tickets, so the field components do more than draw a box. Each one wires up its own label, hint and error, and the rules below hold for every field in the system.

::toc{min=2 max=3}

## Anatomy of a field

Every field has the same parts, in the same order:

1. **Label**, always visible, above the control. Placeholder text is not a label.
2. **Hint**, optional, one sentence of help in `--color-text-muted` at `--font-size-sm`.
3. **Control**, at least 2.5rem (40px) tall with a 1px `--color-neutral-400` border and `--radius-sm` corners.
4. **Error message**, shown only when invalid, with an icon and the words "Error:" for screen readers.

The `Field` component owns the wiring, so you pass a label and a control and it generates the IDs.

```ts title="src/features/invite/InviteForm.tsx"
import { useState } from "react"
import { Field, Input, Button } from "@tideline/react"

export function InviteForm({ onInvite }: { onInvite: (email: string) => void }) {
  const [email, setEmail] = useState("")
  const invalid = email !== "" && !email.includes("@")

  return (
    <form
      onSubmit={(event) => {
        event.preventDefault()
        onInvite(email)
      }}
    >
      <Field
        label="Work email"
        hint="We will send the invitation here."
        error={invalid ? "Enter an address like sam@northwind.example." : undefined}
      >
        <Input type="email" name="email" autoComplete="off" value={email} onChange={(event) => setEmail(event.target.value)} />
      </Field>
      <Button type="submit">Send invitation</Button>
    </form>
  )
}
```

## Text input

Use for single-line values of up to about 80 characters. Set `type` and `inputmode` to match the data: `email`, `url`, `tel`, or `inputmode="numeric"` for codes. Keep the field's width proportional to the expected answer; a 5-digit postcode should not span 600px.

| State | Border | Background | Notes |
| :---- | :----- | :--------- | :---- |
| Default | `--color-neutral-400` | `--color-neutral-0` | 3.2:1 against the page |
| Hover | `--color-neutral-500` | `--color-neutral-0` | |
| Focus | `--color-accent-500`, 2px | `--color-neutral-0` | Plus the 2px outer ring |
| Invalid | `--color-danger-600`, 2px | `#FBE9E9` | Icon and message, never colour alone |
| Disabled | `--color-neutral-200` | `--color-neutral-50` | Exempt from contrast, but avoid it |

### Hints and placeholders

A hint answers a question the person is likely to have before they type: the format ("Use the email on your Zendesk account"), the limit ("Up to 200 characters") or why we ask. Keep it to one sentence. A placeholder may show an example value, such as `sam@northwind.example`, but it disappears on input and has weak contrast, so it must never carry a requirement the person needs to remember. Placeholder text is `--color-neutral-500` and nothing lighter.

## Textarea

Use for answers longer than one line, such as a feedback description. It starts at 3 rows and grows with its content up to 12 rows, then scrolls. If a limit applies, show a live counter such as "412 of 2,000 characters" and announce it politely, once every 50 characters, not on every keystroke.

## Select, checkbox and radio

:::::accordion{name=choice-controls}
:::details[Select]
Use a native select for 5 to 15 options with no search. Below 5 options, use radios so that every choice is visible. Above 15, use the combobox with a type-ahead filter. Do not use a select for two options; a checkbox or switch is faster.
:::
:::details[Checkbox]
Use for independent yes/no choices and for choosing several items from a list. The label is clickable, the hit area is at least 24px, and a group of related checkboxes sits in a `fieldset` with a `legend`. A parent checkbox that selects all children shows the mixed state with `aria-checked="mixed"`.
:::
:::details[Radio group]
Use when exactly one option must be chosen and there are fewer than 5. Preselect the safest option, or leave it empty if there is no safe default and the field is required. Arrow keys move between options; Tab leaves the group.
:::
:::::

## Validation

Validate on blur for format errors, and on submit for everything. Do not show an error while the person is still typing their first attempt. After a field has been flagged, re-validate on every change so the message clears as soon as it is fixed.

Write messages that say what to do, not what went wrong: "Enter a date in the format 14/10/2026" beats "Invalid date". Never blame the person.

Keep what the person typed. A failed submit must not clear the form, and a field that was valid before the error stays valid. On the import wizard we measured that people who lost their column mapping to a validation error abandoned the flow roughly three times as often as those who did not.

:::callout[Required fields]{type=tip}
Most fields in Tidepool are required, so mark the optional ones with "(optional)" in the label instead of putting asterisks everywhere. Say so at the top of the form when it is not obvious.
:::

### Error summary

When a submit fails with more than one error, show a summary at the top of the form and move focus to it. The summary is an element with `role="alert"` and a heading such as "There are 3 problems with your import". Each item is a link that moves focus to the field it names. Keep the inline messages too: the summary is how you find the errors, the inline message is how you fix them.

```ts title="src/features/import/ErrorSummary.tsx"
import { useEffect, useRef } from "react"

type FieldError = { fieldId: string; message: string }

export function ErrorSummary({ errors }: { errors: FieldError[] }) {
  const heading = useRef<HTMLHeadingElement>(null)

  useEffect(() => {
    if (errors.length > 0) heading.current?.focus()
  }, [errors])

  if (errors.length === 0) return null

  return (
    <section role="alert" className="error-summary">
      <h2 ref={heading} tabIndex={-1}>
        There {errors.length === 1 ? "is 1 problem" : `are ${errors.length} problems`} with your import
      </h2>
      <ul>
        {errors.map((error) => (
          <li key={error.fieldId}>
            <a href={`#${error.fieldId}`}>{error.message}</a>
          </li>
        ))}
      </ul>
    </section>
  )
}
```

## Autocomplete

Set the `autocomplete` token on any field that asks for information about the person. It lets browsers and password managers fill the form, and it is required by WCAG 1.3.5.

| Field | Token |
| :---- | :---- |
| Full name | `name` |
| Work email | `email` |
| Organisation | `organization` |
| Job title | `organization-title` |
| New password | `new-password` |
| Current password | `current-password` |
| One-time code | `one-time-code` |

## Do and don't

| Do | Don't |
| :- | :---- |
| Keep one column of fields on screens narrower than 48rem. | Put two fields per row on mobile. |
| Use `autocomplete` tokens so browsers fill known data. | Disable paste in password or email fields. |
| Keep the submit button enabled and explain problems on press. | Disable submit until the form is valid. |
| Group a related set (an address) in a `fieldset` and `legend`. | Rely on spacing alone to show that fields belong together. |

## Accessibility

Each control has a programmatically associated label (WCAG 1.3.1, 3.3.2 and 4.1.2). The `Field` component links the hint and the error to the control with `aria-describedby`, in that order, and sets `aria-invalid="true"` on the control while the error is showing. After a failed submit, focus moves to the error summary (WCAG 3.3.1). Autocomplete attributes satisfy 1.3.5 Identify Input Purpose. Our [Accessibility checklist](doc:Accessibility checklist) has the full list, and [Buttons](doc:Buttons) covers the submit action.
