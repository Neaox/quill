# Accessibility checklist

Run through this list before a component or screen is marked ready for release. It is not the whole of WCAG; it is the set of problems we actually find in review, in the order we find them. We target WCAG 2.1 level AA across Tidepool and Skiff.

## Perceivable

- [ ] Text has at least 4.5:1 contrast against its background, or 3:1 for large text (1.4.3).
- [ ] Interface borders, icons and focus rings have at least 3:1 against what they sit on (1.4.11).
- [ ] No information is carried by colour alone: statuses also have an icon or a word (1.4.1).
- [ ] Every non-decorative graphic has a text alternative, and decorative ones are `aria-hidden` (1.1.1).
- [ ] The page works at 320px wide and with text zoomed to 200%, with no horizontal scrolling for reading text (1.4.4, 1.4.10).
- [ ] The heading levels describe the structure and never skip (1.3.1).

The values for the [Colour](doc:Colour) tokens are already checked in pairs. A new pairing is not covered until you measure it.

## Operable

- [ ] Everything that can be done with a mouse can be done with a keyboard (2.1.1).
- [ ] Focus is always visible, and the order follows the reading order (2.4.7, 2.4.3).
- [ ] Focus never gets trapped, except inside a modal dialog, where Escape closes it and returns focus to the trigger (2.1.2).
- [ ] Links and buttons say what they do without surrounding context ("Download report", not "Click here") (2.4.4).
- [ ] Animations of more than 5 seconds can be paused, and nothing flashes more than 3 times a second (2.2.2, 2.3.1).
- [ ] Motion respects `prefers-reduced-motion`.

## Understandable

- [ ] The page language is set with `lang` (3.1.1).
- [ ] Every input has a visible label, and errors say what to do to fix them (3.3.2, 3.3.3).
- [ ] Inputs that ask about the person carry an `autocomplete` token (1.3.5).
- [ ] Navigation appears in the same place on every page (3.2.3).
- [ ] Opening a menu or changing a select does not navigate away or submit a form (3.2.2).

The patterns for labels, errors and tokens are in [Form fields](doc:Form fields).

## Robust

- [ ] Elements use the right HTML: `button`, `a`, `nav`, `main`, `table` with `th` (4.1.2).
- [ ] Status messages, such as "12 items imported", are announced through a live region without taking focus (4.1.3).
- [ ] The component passes `axe` with no violations in its Storybook story.

## Testing

Test in this order, and stop at the first failure.

1. **Keyboard only.** Unplug the mouse. Reach and operate every control with :kbd[Tab], :kbd[Shift+Tab], :kbd[Enter], :kbd[Space] and the arrow keys.
2. **Screen reader.** VoiceOver with Safari on macOS, and NVDA with Firefox on Windows. On Skiff, VoiceOver on iOS and TalkBack on Android.
3. **Zoom and reflow.** Zoom the browser to 400%, which is the same as 320px at 1280px wide.
4. **Reduced motion and high contrast.** Turn on both in the operating system and check that nothing disappears.
5. **Automated.** Run axe in Storybook and in the Playwright suite.

```ts title="tests/a11y/button.spec.ts"
import { test, expect } from "@playwright/test"
import AxeBuilder from "@axe-core/playwright"

test("button story has no axe violations", async ({ page }) => {
  await page.goto("/iframe.html?id=components-button--primary")
  const results = await new AxeBuilder({ page }).withTags(["wcag2a", "wcag2aa"]).analyze()
  expect(results.violations).toEqual([])
})
```

:::callout[Automation finds about a third]{type=note}
Automated tools catch roughly a third of the issues. A passing axe run means the first box is ticked, not all of them. Tab through the component yourself before you ask for review.
:::

## Reporting a problem

File an issue in the Tideline repository with the label `a11y`, the criterion number and the component. Problems against level A block release. Problems against AA are fixed in the next sprint.
