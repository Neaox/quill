# Decision: SQLite for the local store

**Status:** Accepted, 18 November 2025. **Deciders:** Jonas Weber, Marcus Lee.

## Context

Skiff needs a local database that holds every note a user can see, an outbox of unsent changes and the metadata of voice recordings, and that survives crashes and OS upgrades. A heavy user at Lantern Logistics has about 6,000 notes. Lists must stay smooth at that size.

## Decision

Use SQLite, through `op-sqlite` with SQLCipher encryption, and Kysely for typed queries. Schema changes are numbered migrations that run at app start inside a transaction.

## Why

- **Transactions.** A note and its outbox row must be written together or not at all. The sync design depends on it, see [Offline sync design](doc:Offline sync design).
- **Queries.** Filtering by tag and date over 6,000 rows is a SQL `where`, not a loop in JavaScript. The Inbox query runs in 4 ms.
- **Encryption.** Harbourview Health requires encryption at rest; SQLCipher gives it with one key held in the Keychain or Keystore.
- **Familiarity.** The team already knows SQL, and PostgreSQL habits carry over.

## Rejected

Realm and WatermelonDB add their own object model and sync assumptions. AsyncStorage and MMKV are key-value stores with no transactions across keys and no queries.
