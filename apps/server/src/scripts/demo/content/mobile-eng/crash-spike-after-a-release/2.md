# Crash spike after a release

Use this when Sentry alerts that crash-free sessions for a Skiff release have fallen below 99%, or when support reports several users crashing on launch after an update. Skiff cannot be rolled back: once a binary is in a store it stays there. What you can do is stop it spreading, and ship a fix. The whole point of a staged rollout, described in [Release process](doc:Release process), is that you reach this runbook while 5% or 20% of users have the build, not 100%.

> [!IMPORTANT]
> Pause first, investigate second. A paused rollout costs nothing; every extra hour at 20% puts the crash in front of more people, and those people are in the field, mid-note.

## Steps

1. **Confirm the alert is real.** Open Sentry, Releases, and pick the new release. Compare crash-free sessions with the previous release over the same hours. You need at least 500 sessions on the new build before a percentage means anything. If you have fewer, check the absolute crash count and the number of distinct users.
2. **Pause the rollout.** In Play Console, open the release and choose Halt rollout. In App Store Connect, open the version and choose Pause Phased Release. Both take effect within minutes and do not affect users who already updated.
3. **Tell people.** Post in `#skiff-releases` with the release number, the crash-free figure and "rollout paused". Tell support (Tom Becker's team) in `#support-escalations` so they stop guessing at causes.
4. **Find the top crash.** In Sentry sort issues by users affected. Look at the device, operating system and architecture breakdown first: a crash that affects one phone model or one Android version is almost always a native problem.
5. **Decide how to fix it.** Choose one:
   - **Server-side mitigation**, if a kill switch controls the code that crashes (see below). Turn it off in the remote config console. This is the fastest route and needs no release.
   - **Hotfix**, a new build from the release branch with the smallest possible change. Follow the hotfix path in [Release process](doc:Release process).
   - **Revert and re-release**, if the cause is unclear: cut a new version number from the previous release's commit.
6. **Verify.** When the fix is live, check that crash-free sessions for the fixed build match the previous release's before resuming the rollout.
7. **Resume the rollout** in the same console, at the percentage where you paused it.

> [!WARNING]
> Do not skip the verification in step 6 because the fix "obviously works". The 2026.4 hotfix fixed one crash and exposed a second one that had been hidden behind it.

## Thresholds

| Crash-free sessions, new release | Action |
| :------------------------------- | :----- |
| 99.0% or higher | Normal. Continue the rollout. |
| 98.0% to 99.0% | Hold at the current percentage and investigate. |
| Below 98.0% | Pause immediately (step 2). |

## Kill switches

Three features can be disabled from the remote config console without a release: silence trimming, background audio upload and the Themes tab. Each is cached for 24 hours. Any new native code that runs at start-up or while recording must ship behind a switch.

:::callout[What happened with 2026.8]{type=info}
Silence trimming shipped in 2026.8 and crashed on 32-bit ARM Samsung devices, which our test phones did not include. Crash-free sessions were 97.1% at the 20% stage. The on-call engineer paused 38 minutes after the alert, turned off the trimming switch, and crash-free sessions returned to 99.6% within a day. The fix to the native library shipped in 2026.8.1.
:::

## Who decides

The mobile on-call engineer (see [Mobile on-call guide](doc:Mobile on-call guide)) can pause a rollout without asking anyone. Resuming, reverting and shipping a hotfix need the release manager, and for the iOS review a second approver in App Store Connect.

## Afterwards

If more than 1% of active users crashed, or the build was live for more than 4 hours before the pause, write a postmortem. Use the platform team's process in [Incident response process](doc:Incident response process) for severity and timelines.
