# RFC-012: Adopt the React Native new architecture

**Status:** Accepted, 3 March 2026. Shipped on iOS in 2026.6 and on Android in 2026.7. **Author:** Jonas Weber. **Deciders:** Marcus Lee, Jonas Weber, Skiff mobile team.

## Context

Skiff still runs on the legacy bridge. Every call between JavaScript and native code is serialised to JSON and queued, and three things now hurt:

- Cold start on a Pixel 6a is 1.7 s against a 2.0 s budget, and about 350 ms of that is native module initialisation, which the bridge does eagerly for all 14 modules.
- Scrolling an Inbox of 2,000 notes drops 31 frames in our standard scroll test, because list items are measured asynchronously.
- Our native modules are untyped at the boundary. In the last two quarters, 4 of the 11 crashes we investigated came from a JS call whose arguments did not match the native signature.

React Native's current releases are built for the new architecture, with Fabric for rendering and TurboModules for native modules. The legacy path is in maintenance and will be removed in a future version.

## Decision

Adopt the new architecture for Skiff, one platform at a time, iOS first. Turn it on behind a build flag in the 2026.4 beta, and ship it to everyone in 2026.6 (iOS) and 2026.7 (Android) if the criteria below hold. The criteria are:

1. Cold start no worse than today on both reference devices.
2. Crash-free sessions no lower than the previous release at each rollout stage.
3. Every dependency either supports the new architecture or has a named replacement.

## Consequences

- Native modules are rewritten as TurboModules with TypeScript specs, which turns signature mismatches into build failures. We have two of our own (recorder and background upload) plus secure storage.
- We upgrade React Native by one minor version each quarter instead of falling further behind. Budget: about 3 engineer-days a quarter.
- We will have to replace or upgrade 5 of our 41 dependencies.
- For two release cycles we carry a build flag and two code paths for the three native modules.
- The old remote debugger goes away in favour of the Hermes debugger.

## Alternatives considered

::::accordion{name=rfc-012-alternatives}
:::details[Stay on the legacy bridge and optimise]
We could lazy-load native modules and add a list library with fixed item heights, which would fix perhaps half of the start-up and scroll cost. It would not fix the untyped boundary, and the work would be thrown away when we migrate.
:::
:::details[Rewrite Skiff as two native apps]
Swift and Kotlin apps would give the best recording and background behaviour. They would also need two teams: we have seven mobile engineers, most with a web background. Rejected on cost alone.
:::
:::details[Move to Flutter]
Flutter has a mature rendering engine and typed plugins. It would mean rewriting every screen and the sync engine in Dart, and abandoning the TypeScript we share with Tidepool's API client.
:::
:::details[Wait until the legacy path is removed]
Waiting forces a big-bang migration under a deadline we do not control. Doing it now, one platform at a time, lets us stop if the numbers go the wrong way.
:::
::::

## Prototype results

A 10-day prototype on iOS, with the three native modules ported, gave cold start 1.4 s on an iPhone 12 against 0.9 s today (the prototype did not yet lazy-load anything) and 15 dropped frames in the scroll test. The cold start regression was explained and fixed; the scroll result is the reason for this proposal.

## Outcome

Both criteria that could fail were met. Measured on the 2026.6 release, against 2026.1:

- Cold start: 1.7 s to 1.5 s on the Pixel 6a, and 0.9 s to 0.8 s on the iPhone 12.
- Inbox scroll: 31 to 14 dropped frames.
- Crash-free sessions held at 99.6% through the 5%, 20% and 100% stages on iOS, and 99.5% on Android.
- Four dependencies were upgraded and one, the image cache, was replaced. The Android rollout slipped by one release because of it.

The build flag was removed in 2026.8. See [Skiff app architecture](doc:Skiff app architecture) for the current shape of the app.
