# RFC-012: Adopt the React Native new architecture

**Status:** Proposed, 9 February 2026. **Author:** Jonas Weber. **Deciders:** Marcus Lee, Jonas Weber, Skiff mobile team.

## Context

Skiff still runs on the legacy bridge. Every call between JavaScript and native code is serialised to JSON and queued, and three things now hurt:

- Cold start on a Pixel 6a is 1.7 s against a 2.0 s budget, and about 350 ms of that is native module initialisation, which the bridge does eagerly for all 14 modules.
- Scrolling an Inbox of 2,000 notes drops 31 frames in our standard scroll test, because list items are measured asynchronously.
- Our native modules are untyped at the boundary. In the last two quarters, 4 of the 11 crashes we investigated came from a JS call whose arguments did not match the native signature.

React Native's current releases are built for the new architecture, with Fabric for rendering and TurboModules for native modules. The legacy path is in maintenance and will be removed in a future version. Staying put is possible for now, but each upgrade gets harder to take.

## Decision

Adopt the new architecture for Skiff, one platform at a time, iOS first. Turn it on behind a build flag in the 2026.4 beta, and ship it to everyone in 2026.6 (iOS) and 2026.7 (Android) if the criteria below hold. The criteria are:

1. Cold start no worse than today on both reference devices.
2. Crash-free sessions no lower than the previous release at each rollout stage.
3. Every dependency either supports the new architecture or has a named replacement.

## Consequences

- Native modules are rewritten as TurboModules with TypeScript specs, which turns signature mismatches into build failures. We have two of our own (recorder and background upload) plus secure storage.
- We upgrade React Native by one minor version each quarter instead of falling further behind. Budget: about 3 engineer-days a quarter.
- We will have to replace or upgrade 5 of our 41 dependencies. The audit is in the team's wiki.
- For two release cycles we carry a build flag and two code paths for the three native modules.
- Debugging tools change: the old remote debugger goes away in favour of the Hermes debugger.

## Alternatives considered

::::accordion{name=rfc-012-alternatives}
:::details[Stay on the legacy bridge and optimise]
We could lazy-load native modules and add a list library with fixed item heights, which would fix perhaps half of the start-up and scroll cost. It would not fix the untyped boundary, and the work would be thrown away when we migrate. Cheapest this quarter, most expensive over the year.
:::
:::details[Rewrite Skiff as two native apps]
Swift and Kotlin apps would give the best recording and background behaviour. They would also need two teams: we have seven mobile engineers, most with a web background. Feature parity with Tidepool would slow to a crawl. Rejected on cost alone.
:::
:::details[Move to Flutter]
Flutter has a mature rendering engine and typed plugins. It would mean rewriting every screen and the sync engine in Dart, and abandoning the TypeScript we share with Tidepool's API client. The migration would take an estimated 8 months of the whole team.
:::
:::details[Wait until the legacy path is removed]
Waiting forces a big-bang migration under a deadline we do not control. Doing it now, one platform at a time, lets us stop if the numbers go the wrong way.
:::
::::

## Prototype results

A 10-day prototype on iOS, with the three native modules ported, gave: cold start 1.4 s on an iPhone 12 for the prototype build against 0.9 s today (the prototype did not yet lazy-load anything), and 15 dropped frames in the scroll test. The cold start regression is explained and fixable; the scroll result is the reason for this proposal.
