# Release checklist

Work through this on the Friday before submission, on the release branch. The release manager ticks items in the release's tracking issue; anyone can add an item after a miss. The surrounding steps are in [Release process](doc:Release process).

## Before you submit

- [ ] CI is green on `release/YYYY.M` for iOS and Android, including the end-to-end suite.
- [ ] Crash-free sessions in the beta are 99% or higher over at least 500 sessions.
- [ ] Version name and build numbers are unique and higher than the live release.
- [ ] A fresh install syncs against the staging API, and a note made offline reaches it.
- [ ] A 3-minute voice note records, uploads and returns a transcript on a Pixel 6a and an iPhone 12.
- [ ] An upgrade from the previous release keeps the local database and runs its migration.
- [ ] Cold start is within budget on both reference devices.
- [ ] Remote config kill switches for new native code are in place and tested off.
- [ ] Release notes are written for both store listings, and the changelog entry is drafted.
- [ ] Privacy answers match any change to data collected.

## After you submit

- [ ] Post the build numbers in `#skiff-releases`.
- [ ] Tell support what is changing, in two sentences they can paste to a customer.
- [ ] Put the rollout dates in the on-call calendar.
