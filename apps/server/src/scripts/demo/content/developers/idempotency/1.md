# Idempotency

Networks fail between the moment you send a request and the moment you read the answer. If a `POST` times out, you cannot tell whether Tidepool created the item. An idempotency key makes it safe to try again.

## Send a key

Add an `Idempotency-Key` header with a unique value, such as a UUID v4, to any `POST` request.

```bash
curl https://api.tidepool.example/v2/feedback \
  -H "Authorization: Bearer $TIDEPOOL_TOKEN" \
  -H "Idempotency-Key: 0b7d6f52-91c4-4a6e-8f0b-3c2a5e7d9b14" \
  -H "Content-Type: application/json" \
  -d '{"body":"Please add SSO for the roadmap","source":"api"}'
```

Tidepool stores the status code and body of the first response for 24 hours. Repeat the request with the same key and the same body and you get that stored response back, with an extra `Idempotency-Replayed: true` header. Nothing is created twice.

## What can go wrong

| Situation | Response |
| :-------- | :------- |
| Same key, same body, first request finished | The stored response, replayed |
| Same key, first request still running | `409` with code `idempotency_in_progress`; wait and retry |
| Same key, different body or path | `422` with code `idempotency_key_reuse` |

Keys are scoped to your workspace. `GET` and `DELETE` are already safe to repeat, so the header is ignored on them. Responses with a `5xx` status are not stored, so a retry gets a fresh attempt.

Generate the key once per logical operation and reuse it across every retry of that operation. See [Errors](doc:Errors) for which failures are worth retrying.
