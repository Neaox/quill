# Webhooks

Webhooks let Tidepool call your server when something changes, so you do not have to poll. Each delivery is an HTTPS `POST` with a JSON body and a signature you verify before trusting it.

## Create an endpoint

Register a URL with `POST /v2/webhook-endpoints`. The token needs the `webhooks:manage` scope, and the URL must be HTTPS and publicly reachable.

```bash
curl https://api.tidepool.example/v2/webhook-endpoints \
  -H "Authorization: Bearer $TIDEPOOL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://hooks.northwind.example/tidepool",
    "events": ["feedback.created", "roadmap_item.status_changed"],
    "description": "Sync feedback to the data warehouse"
  }'
```

The response is `201 Created`. It includes the endpoint `id` (`we_01JA3F7K2D`) and a `secret` beginning with `whsec_`. The secret is returned once; store it next to your other credentials. Omit `events` to subscribe to everything, and use `["*"]` if you want future event types too.

## Events

:::table[Event types]{width=wide caption=bottom}
| Event | Sent when |
| :---- | :-------- |
| `feedback.created` | An item arrives from any source: ticket, interview, widget, CSV import or API |
| `feedback.updated` | The body, tags, author or theme of an item changes |
| `feedback.deleted` | An item is deleted |
| `theme.created` | A theme is created, by a person or by clustering |
| `roadmap_item.status_changed` | A roadmap item moves between `planned`, `in_progress`, `shipped` and `archived` |
| `roadmap_item.published` | A roadmap item becomes visible on the public roadmap |
:::

## What a delivery looks like

```json
{
  "id": "evt_01JA4B8M5Q",
  "type": "feedback.created",
  "created_at": "2026-10-09T08:15:42Z",
  "data": {
    "object": {
      "id": "fb_01JA4B8M3X",
      "body": "Dark mode for the roadmap page",
      "source": "widget",
      "theme_id": null,
      "created_at": "2026-10-09T08:15:42Z"
    }
  }
}
```

The `id` is unique per event and stays the same across retries. Use it to discard duplicates.

## Verify the signature

Every delivery carries a `Tidepool-Signature` header:

```
Tidepool-Signature: t=1760001342,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
```

`t` is the Unix time of the attempt, and `v1` is a hex HMAC-SHA256 of the string `t + "." + rawBody`, keyed with your endpoint's secret. Compute it over the raw bytes you received, not over re-serialised JSON, compare in constant time, and reject timestamps more than five minutes old.

:::code-group
```ts [TypeScript]
import { createHmac, timingSafeEqual } from "node:crypto"

export function verify(rawBody: string, header: string, secret: string): boolean {
  const parts = Object.fromEntries(header.split(",").map((p) => p.split("=")))
  if (Math.abs(Date.now() / 1000 - Number(parts.t)) > 300) return false
  const expected = createHmac("sha256", secret).update(`${parts.t}.${rawBody}`).digest()
  const received = Buffer.from(parts.v1 ?? "", "hex")
  return received.length === expected.length && timingSafeEqual(received, expected)
}
```
```py [Python]
import hashlib, hmac, time

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if abs(time.time() - int(parts["t"])) > 300:
        return False
    signed = parts["t"].encode() + b"." + raw_body
    expected = hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))
```
:::

> [!IMPORTANT]
> Verify before you parse. A body that fails verification should get a `400` and no further processing.

## Respond and retry

Return any `2xx` status within 10 seconds. Do the real work after you respond, for example by putting the event on a queue. Anything else, including a timeout, counts as a failure and Tidepool retries with exponential backoff: after 1 minute, then 5 minutes, 30 minutes, 2 hours and 6 hours, for 6 attempts over about 8 hours.

:::details[Why did my endpoint stop receiving events?]
When 10 consecutive events exhaust all 6 attempts, Tidepool marks the endpoint `disabled` and emails the workspace admins. Fix the problem, then re-enable it with `PATCH /v2/webhook-endpoints/we_01JA3F7K2D` and `{"status": "enabled"}`. Events sent while it was disabled are not replayed.
:::

:::details[Are events delivered in order?]
No. Two events about the same item can arrive out of order, especially after a retry. Compare `created_at` on the event, or fetch the current object by `id`, before overwriting your own data.
:::

Pair webhooks with [Idempotency](doc:Idempotency) on your own side: handling the same `evt_` id twice should have no effect.
