# Pagination

Every endpoint that returns a list uses cursor pagination, so results stay stable while new items arrive. Offset pagination (`page` and `per_page`) existed in v1 and does not in v2.

## Parameters and response

| Parameter | Meaning |
| :-------- | :------ |
| `limit` | Items per page, from 1 to 100. Defaults to 25. |
| `cursor` | The `next_cursor` from the previous response. Omit it for the first page. |

A list response has three fields: `data`, `has_more` and `next_cursor`. When `has_more` is `false`, `next_cursor` is `null` and you are done. Treat the cursor as an opaque string. It expires after 24 hours, after which the API returns `400` with the code `invalid_cursor`.

## Walk every page

:::code-group
```ts [TypeScript]
let cursor: string | undefined
do {
  const page = await tidepool.feedback.list({ limit: 100, cursor })
  for (const item of page.data) await process(item)
  cursor = page.next_cursor ?? undefined
} while (cursor)
```
```py [Python]
for item in client.feedback.list(limit=100).auto_paging_iter():
    process(item)
```
```go [Go]
iter := client.Feedback.List(ctx, &tidepool.FeedbackListParams{Limit: 100})
for iter.Next() {
	process(iter.Item())
}
if err := iter.Err(); err != nil {
	return err
}
```
:::

The SDK iterators fetch the next page lazily, so memory stays flat however large the workspace is. Each page is one request against your [rate limit](doc:Rate limits).
