# Migrating from v1 to v2

Version 2 of the API replaces `https://api.tidepool.example/v1`. Most integrations need a day of work, not a rewrite: the resources are the same, but authentication, pagination, naming and errors changed. Work through the sections below in order.

## 1. Switch the base URL and authentication

v1 used an `X-API-Key` header with a key you created in account settings. v2 uses a bearer token with scopes. Create one in **Settings → API → Tokens**; see [Authentication](doc:Authentication).

```diff
- curl https://api.tidepool.example/v1/comments \
-   -H "X-API-Key: tp_key_83hd92kd"
+ curl https://api.tidepool.example/v2/feedback \
+   -H "Authorization: Bearer $TIDEPOOL_TOKEN"
```

## 2. Rename resources and fields

| v1 | v2 |
| :-- | :-- |
| `/comments` | `/feedback` |
| `/topics` | `/themes` |
| `/roadmap` | `/roadmap-items` |
| `text` | `body` |
| `topic_id` | `theme_id` |
| `created` (Unix seconds) | `created_at` (ISO 8601, UTC) |

```diff
  {
-   "id": 48213,
-   "text": "Export to CSV times out on large workspaces",
-   "topic_id": 311,
-   "created": 1759760529
+   "id": "fb_01J9ZK3Q7M",
+   "body": "Export to CSV times out on large workspaces",
+   "theme_id": "thm_01J9Y2H8RA",
+   "created_at": "2026-10-06T14:22:09Z"
  }
```

IDs are now strings with a prefix. Store them as strings, never as integers. v1 numeric IDs are accepted in the path of a v2 `GET` for 12 months and resolve to the same object.

## 3. Replace offset pagination with cursors

v1 returned `page` and `per_page` and a `total`. v2 has no total, because computing one on a large workspace is slow. Follow `next_cursor` until `has_more` is `false`.

```diff
- GET /v1/comments?page=3&per_page=50
+ GET /v2/feedback?limit=50&cursor=eyJpZCI6ImZiXzAxSjlaSzNRN00ifQ
```

The details are in [Pagination](doc:Pagination).

## 4. Handle the new error shape

v1 errors were a bare string: `{"error": "bad request"}`. v2 returns an object with `type`, `code`, `message`, `param` and `request_id`. Branch on `code`.

:::details[What if I cannot migrate everything at once?]
You can run both versions side by side. A v1 key and a v2 token can belong to the same workspace and see the same data. Migrate one resource at a time, starting with reads, which are the lowest risk. Writes through v1 and v2 are consistent with each other immediately.
:::

:::details[Are there any behaviour changes I might miss?]
Yes, three. Deleting feedback is now a soft delete that you can undo for 30 days. `PATCH` replaces only the fields you send; v1 treated a missing field as `null`. List endpoints return newest first by default, where v1 returned oldest first.
:::
