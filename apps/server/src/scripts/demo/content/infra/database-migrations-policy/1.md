# Database migrations policy

Tidepool deploys about 14 times a day to a single 2 TB PostgreSQL primary, and Skiff clients in the field can be several releases old. So every schema change must work with the application version before it and the version after it. We get there with expand and contract, and a short list of rules that CI enforces.

## Expand and contract

A change that would break the running code is split across three releases, never one.

1. **Expand.** Add the new column, table or index. Old code ignores it. New code writes to both old and new.
2. **Migrate.** Backfill existing rows, then switch reads to the new shape. Both shapes stay in the database.
3. **Contract.** Once no running version reads the old shape (check the release dashboard, and wait at least one full release cycle), drop it.

Renaming `feedback.body` to `feedback.content` looks like this. Release 2026.10 expands:

```diff
 CREATE TABLE feedback (
   id           uuid PRIMARY KEY,
   workspace_id uuid NOT NULL,
   body         text NOT NULL,
+  content      text,
   created_at   timestamptz NOT NULL DEFAULT now()
 );
```

The application writes both columns. A later release backfills and reads `content`. Release 2026.12 contracts, once nothing reads `body`:

```diff
 CREATE TABLE feedback (
   id           uuid PRIMARY KEY,
   workspace_id uuid NOT NULL,
-  body         text NOT NULL,
-  content      text,
+  content      text NOT NULL,
   created_at   timestamptz NOT NULL DEFAULT now()
 );
```

The second diff shows the end state; the migration itself is an `ALTER TABLE ... DROP COLUMN`, written in its own file.

## Rules

- **Migrations are forward only.** We do not write down migrations. A bad migration is fixed by another migration.
- **Run before the rollout.** Migrations run as a job before Argo Rollouts shifts traffic, so a failed migration stops the deploy with the old version still serving.
- **Set a lock timeout.** Every migration starts with `SET lock_timeout = '3s';`. A migration that cannot get its lock in three seconds fails and is retried; it never queues behind a long transaction and blocks every query behind it.
- **Indexes are concurrent.** Use `CREATE INDEX CONCURRENTLY` in its own migration file, because it cannot run inside a transaction.
- **No volatile defaults.** `ADD COLUMN ... DEFAULT now()` is safe on PostgreSQL 16, but a default that calls a volatile function rewrites the table and is rejected.
- **`NOT NULL` in two steps.** Add a `CHECK (col IS NOT NULL) NOT VALID`, validate it in a later migration, then set `NOT NULL`.

```sql
SET lock_timeout = '3s';
ALTER TABLE theme_items
  ADD CONSTRAINT theme_items_confidence_present
  CHECK (confidence IS NOT NULL) NOT VALID;
-- next release:
ALTER TABLE theme_items VALIDATE CONSTRAINT theme_items_confidence_present;
```

## Review

Every migration needs a review from someone on the platform team, plus the author's own checklist in the pull request. CI runs `squawk` against new SQL and fails on any rule above. A reviewer should ask three questions: what lock does this take, how long on the biggest table, and what does the previous release do when it runs against this schema?

:::callout[Exceptions]{type=info}
A rule can be waived with a `-- squawk-ignore: <rule>` comment and a sentence of reasoning in the pull request. Waivers are rare; Marcus Lee reads each one.
:::

Rolling back an application release does not roll back the schema. That is the point of the expand step.
