# Secrets rotation

Every production secret lives in AWS Secrets Manager. The External Secrets Operator copies each one into a Kubernetes Secret in the `tidepool` namespace, and Stakater Reloader restarts the pods that mount it. This runbook covers the scheduled rotation, which Aisha Khan's team tracks for the SOC 2 audit, and the emergency rotation after a suspected leak.

## Schedule

| Secret | Used by | Rotated | Overlap |
| :----- | :------ | :------ | ------: |
| `tidepool/prod/database-app` | api, worker | Every 90 days, automatic | 24 h |
| `tidepool/prod/session-signing-key` | gateway, api | Every 90 days | 7 days |
| `tidepool/prod/sso-broker-client` | api | Every 180 days | 24 h |
| `tidepool/prod/webhook-signing-seed` | webhooks | Every 180 days | 30 days |
| `tidepool/prod/zendesk-oauth` | worker | Every 365 days | 1 h |

"Overlap" is how long the old value keeps working after the new one is live. It is not optional: since the [2 September login errors](doc:Postmortem: 2 September login errors), no secret is revoked in the same step that issues its replacement.

> [!WARNING]
> Never revoke the old secret before every pod reports the new one. A pod that has not restarted yet is still using the old value, and revoking it logs out or breaks everyone it serves.

## Rotate a secret

1. **Open a change.** Create a ticket tagged `secrets-rotation` and post in `#platform`. Do this in the Tuesday to Thursday window, never on a Friday and never during a release freeze.

2. **Create the new version** as `AWSPENDING`, leaving the current one as `AWSCURRENT`.

   ```bash
   aws secretsmanager put-secret-value \
     --secret-id tidepool/prod/sso-broker-client \
     --secret-string file://new-secret.json \
     --version-stages AWSPENDING
   ```

3. **Register the new value with the other side.** For the SSO broker, add the second client secret in the identity provider's console. Both values are now valid there.

4. **Promote the new version** so the operator picks it up. The Operator refreshes every 10 minutes; force it to refresh now.

   ```bash
   aws secretsmanager update-secret-version-stage \
     --secret-id tidepool/prod/sso-broker-client \
     --version-stage AWSCURRENT --move-to-version-id "$NEW_VERSION_ID"
   kubectl -n tidepool annotate externalsecret sso-broker-client \
     force-sync="$(date +%s)" --overwrite
   ```

5. **Confirm every pod restarted.** Reloader rolls the deployments; wait for all of them.

   ```bash
   kubectl -n tidepool rollout status deploy/api
   kubectl -n tidepool get pods -l app=api \
     -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.startTime}{"\n"}{end}'
   ```

   Every start time must be later than step 4.

6. **Watch for an hour.** Check the login success rate and the `auth_failures_total` panel on the Platform dashboard. A rise means some pods still hold the old value.

7. **Revoke the old value** only after the overlap in the table has passed: remove it from the identity provider and delete the `AWSPREVIOUS` version.

8. **Close the ticket** with the secret name, the dates and the version IDs. Add one line to the SOC 2 evidence sheet.

## Emergency rotation

If a secret may have leaked, skip the overlap and accept the disruption. Page the incident commander first (see [Incident response process](doc:Incident response process)), rotate, restart everything that mounts it, and revoke the old value immediately.
