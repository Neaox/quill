# Multi-region failover

Use this runbook when `us-east-1` cannot serve Tidepool and the incident commander has decided to move production to `eu-west-1`. The targets are a recovery time of 45 minutes and a recovery point of 5 minutes. It needs two people: an operator who runs the commands and a second engineer who reads each one back before it is run.

## When to fail over

Fail over when **both** of these hold:

- AWS reports an event affecting EKS, RDS or networking in `us-east-1`, or the gateway error rate has been above 50% for 10 minutes with a regional cause; and
- there is no credible recovery estimate under 30 minutes.

Do not fail over for a single bad service, a bad deploy (roll back instead) or a database problem that a Multi-AZ failover will fix in two minutes. The decision belongs to the incident commander together with the on-call engineering manager, currently Marcus Lee.

> [!WARNING]
> Failing over is a one-way door for the next several hours. Failing back needs a planned window, a fresh replica and roughly ten hours of replication, so do not use a failover to "test" a fix.

## Before you start

You need the `platform-admin` role in AWS SSO and two kubectl contexts, `tide-use1-prod` and `tide-euw1-prod`. First check that the replica is healthy and how far behind it is.

```bash
aws rds describe-db-instances --region eu-west-1 \
  --db-instance-identifier tide-prod-replica \
  --query 'DBInstances[0].[DBInstanceStatus,StatusInfos]'

psql "$EUW1_REPLICA_URL" -c \
  "select now() - pg_last_xact_replay_timestamp() as replay_lag;"
```

:::callout[Replay lag above 5 minutes]{type=caution}
Anything the primary committed in the last few minutes is lost on promotion. If the lag is over 5 minutes, tell the incident commander the real recovery point before you go on; they may choose to wait for the region instead.
:::

## Steps

1. **Announce.** Say in `#incident` that you are starting the failover, and set the status page to "Investigating: we are moving Tidepool to our European region". Start a timer; the 45 minutes run from this moment.

2. **Freeze deploys.** Stop Argo CD changing the standby while you work on it.

   ```bash
   argocd app set tidepool-euw1 --sync-policy none
   ```

3. **Promote the replica.** Promotion takes six to eight minutes. The promoted instance keeps its endpoint, so the standby's `DATABASE_URL` needs no change.

   ```bash
   aws rds promote-read-replica --region eu-west-1 \
     --db-instance-identifier tide-prod-replica
   aws rds wait db-instance-available --region eu-west-1 \
     --db-instance-identifier tide-prod-replica
   ```

4. **Scale up the standby.** It normally runs a quarter of production. Bring it to full size and wait for the pods.

   ```bash
   for app in gateway:8 api:18 worker:12 webhooks:4 public-site:3; do
     kubectl --context tide-euw1-prod -n tidepool \
       scale deploy/"${app%%:*}" --replicas="${app##*:}"
   done
   kubectl --context tide-euw1-prod -n tidepool rollout status deploy/api
   ```

5. **Check the new primary.** The database must accept writes, and the application must be able to write.

   ```bash
   psql "$EUW1_PRIMARY_URL" -c "select pg_is_in_recovery();"   # expect: f
   kubectl --context tide-euw1-prod -n tidepool exec deploy/api -- \
     node scripts/smoke-write.js
   ```

6. **Shift traffic.** Set the `us-east-1` record's weight to 0 and the `eu-west-1` weight to 100. The records have a 60-second TTL.

   ```bash
   aws route53 change-resource-record-sets \
     --hosted-zone-id Z0EXAMPLE1234 \
     --change-batch file://failover/to-euw1.json
   ```

7. **Verify** with the checks below, then tell `#incident` and update the status page.

## Verify

Within five minutes of the DNS change you should see all of these:

- `https://app.tidepool.example/healthz` returns `200` with `"region": "eu-west-1"`.
- The "Checkout journey" and "Feedback submit" synthetic checks are green from three locations.
- Gateway p95 latency is under 400 ms and the 5xx rate is under 1%.
- Queue depth for `default` is falling.

## What is lost

Redis in `eu-west-1` starts empty. That has three consequences, all accepted:

- Rate limit counters reset, so customers get a fresh allowance.
- Jobs that were queued in `us-east-1` are not replayed. A CSV import that was running must be started again by the customer; Support should tell anyone who asks.
- Webhooks that were queued or retrying are lost. Customers will not see them again unless they ask us to resend.

## Failing back

Do not fail back during the incident. Once `us-east-1` is healthy, plan a window outside business hours on a weekend:

1. Create a new read replica in `us-east-1` from the `eu-west-1` primary and wait for it to catch up (about ten hours for 1.7 TB).
2. Repeat this runbook in reverse, with `eu-west-1` as the source.
3. Rebuild the `eu-west-1` replica from the new primary and re-enable Argo CD sync.
