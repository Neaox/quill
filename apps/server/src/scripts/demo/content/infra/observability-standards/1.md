# Observability standards

A service does not take production traffic until it has a dashboard, an SLO, an alert that pages a person and a log format anyone can search. These are the minimum. Teams may add more, but may not skip these.

## Service level objectives

Every user-facing service has an availability SLO and a latency SLO measured over a rolling 30 days at the gateway, not inside the service. A burn-rate alert fires when we are spending the error budget fast enough to exhaust it in under three days.

| Service | Availability | Latency (p95) | Error budget per 30 days |
| :------ | -----------: | ------------: | -----------------------: |
| API, reads | 99.95% | 300 ms | 21 min |
| API, writes | 99.9% | 600 ms | 43 min |
| Public roadmap pages | 99.9% | 800 ms | 43 min |
| Feedback widget script | 99.95% | 150 ms | 21 min |
| Webhook delivery, first attempt within 60 s | 99% | n/a | 7 h 12 min |
| Skiff sync | 99.5% | 2,000 ms | 3 h 36 min |

Customers on the Pinecrest Bank and Harbourview Health contracts are promised 99.9% for the API; the internal objectives above are stricter on purpose, so we notice before they do.

## Metrics

We use Prometheus conventions. Names are `snake_case`, start with the service, and end with a unit.

| Kind | Name pattern | Example |
| :--- | :----------- | :------ |
| Counter | `<service>_<thing>_total` | `webhooks_deliveries_total` |
| Gauge | `<service>_<thing>` | `worker_queue_depth` |
| Histogram | `<service>_<thing>_seconds` | `api_request_duration_seconds` |
| Age | `<service>_<thing>_age_seconds` | `webhooks_oldest_job_age_seconds` |

Labels describe a small, bounded set of values: `route`, `status_class`, `queue`, `region`. Never label by `workspace_id`, user or URL. A label with more than 100 values is a bug; it is what broke our Prometheus memory in March.

:::callout[Measure the oldest, not the average]{type=tip}
For anything that goes through a queue, alert on the age of the oldest waiting job. An average hides one stuck customer behind thousands of healthy ones.
:::

## Logs

Logs are JSON, one object per line, written to stdout. The collector adds the pod, node and region.

| Field | Required | Notes |
| :---- | :------- | :---- |
| `time` | Yes | ISO 8601 in UTC |
| `level` | Yes | `debug`, `info`, `warn`, `error` |
| `service` | Yes | The deployment name |
| `request_id` | On requests | Created by the gateway and passed on |
| `workspace_id` | When known | A UUID, never a name |
| `msg` | Yes | A constant sentence; put variables in fields |

Do not log request bodies, access tokens, session IDs or customer feedback text. A secret that reaches the logs counts as leaked and is rotated; see [Secrets rotation](doc:Secrets rotation).

## Alerts

Every alert has an owner, a runbook link and a severity that matches the incident definitions in [Incident response process](doc:Incident response process).

| Severity | Who is told | Response | Example |
| :------- | :---------- | :------- | :------ |
| Page | On-call engineer, by phone | Within 5 minutes | Burn rate above 14.4 over one hour |
| Ticket | Owning team's channel | Next working day | Disk will fill in 14 days |
| Info | Dashboard only | None | Deploy finished |

An alert that fired more than twice a month without anyone acting is deleted or retuned at the next monthly review. The platform team keeps the page rate under two pages per engineer per on-call week.
